# Target.Wasm 宿主规范 v1.3

SfW 的 wasm 目标把 Sublimation 程序跑在「QuickJS-in-WASM」宿主里。宿主是 wasm 里的
另一个 JS 世界——它与编译产物之间的边界必须由规范固定，否则任何一边的漂移都表现为
运行期玄学。本文是规范正本；实现见 wasm-app/js/wasm-runtime.js（Node/CJS，已验证）
与 wasm-app/js/wasm-runtime-web.mjs（浏览器/ES，结构性交付）。

> 与 SfA/SfG 的关系：SfA 的宿主是 Android WebView+KT 桥，SfG 的宿主是 KAPLAY 页面；
> 三者共用同一套 ``-A 处理器路线`` 与 `@host` 无体声明机制，差异全在宿主侧——
> SfW 的独有约束是 wasm 没有隐式事件循环与隐式 IO，一切都要宿主显式提供（本规范即此「显式」）。

---

## 0. 规范对象与版本

- 规范版本：v1.3（编译器 t43 把 @host 统一进 __subl.call；宿主裸名别名彻底回撤）
- 版本史：v1.1（t38：ABI 统一为 __subl.call 单入口）→ v1（Phase 1 投产）
- 宿主实现：quickjs-emscripten-core 0.32.0 + `@jitl/quickjs-wasmfile-release-sync`（默认）
  备用 `@jitl/quickjs-singlefile-cjs-release-sync`（wasm 内联、纯 Node）
- 装载环境：Node 18+（验证过 Node 24）；浏览器（结构性交付，本环境未回归）

## 1. 装载契约（C1）

宿主按序执行，任一步失败即终止并分类报告（C5）：

1. `newQuickJSWASMModuleFromVariant(variant)`：实例化 wasm 模块；
2. `module.newContext()`：建上下文（随后按需设 `runtime.setMemoryLimit`）；
3. 注入桥接（C2）；
4. `vm.evalCode(产物)`；
5. **S-1 兼容**：若产物导出了 `__subl.main`（`vm.typeof` 为 function），宿主调用之；
   -A 路线产物（自执行 IIFE）无导出 → 跳过本步（双路线自动适配）；
6. 驱动 pending jobs（C3）；
7. 释放全部 handle（C4）→ `vm.dispose()`。

```
宿主 = 装配者 + 事件循环替代者：产物只声明「要什么」，宿主决定「怎么跑」。
```

## 2. 桥接契约（C2，v1.1：t38 定案的统一 ABI）

**唯一 ABI：`globalThis.__subl.call(op, args)` 单入口 dispatch。**（v1 的「裸名直挂」
已由队长裁决作废——保留统一拦截点供插件框架/处理器 op 白名单/能力门控使用。）

- **生成侧**：调用点一律翻成 `globalThis.__subl.call("<op>", [args...])`。
  - 编译器平台分派（t35/t37）：内建 BRIDGE_OPS（`print` 的 op 为 `"println"`、`getArgs`、`sleep`…）
    与用户 `@wasm @host` 声明（op = 声明的函数名）都走单入口；
  - 产物入口导出合并进宿主已安装的 `__subl` 对象
    （`(globalThis.__subl || (globalThis.__subl = {})).main = ...`），不自执行。
- **宿主侧**：宿主在 evalCode 前安装 `globalThis.__subl.call(op, args)`，
  内部用一个 **op 注册表**（单一真源，OPS：op 名 → 实现）分派：
  - `op`（Str）与 `args`（Sublimation 实参数组）以 QuickJS 句柄到达
    （Node/CJS 宿主；浏览器宿主同构）；dispatcher 提取实参句柄、调用实现、释放（C4）；
  - **桥返回值**只允许原语（自动装箱）或 **handle**（Optional/List/结构体）；
  - **未知 op** 抛明确错误（C5）——「笔误 op」在编译期由处理器 op 白名单拦截、
    运行期由 dispatcher 兜底。
- **形状对齐**：编译器对 Sum 类型的 JS 形状是 `{tag, 0, 1, ...}`、List 是 JS 数组；
  宿主构造返回值必须逐字对齐（`wasmStorageLoad` 造 `{tag:"Some",0:v}`、
  `wasmStorageKeys` 造数组）。
- **布尔**：同步宿主无 `newBoolean`，用内置单例 `vm.true/vm.false`（勿 dispose）。
- **存储桥语义**：键值皆 Str；Node 宿主=进程内 Map，浏览器宿主=localStorage
  （`sfw.storage.v1` 键名，JSON 序列化；无 localStorage 时降级内存态）。
- **统一完成（t43）**：编译器对用户 `@host` 无体声明同样生成
  `__subl.call("<声明名>", [args])`（t40 实测此前仍是裸名调用，上报后由编译器线统一）。
  宿主**不再注入任何桥全局名**（t40 的过渡裸名别名已回撤）。
  桥调用唯一入口 = `__subl.call`，内建桥 op 与 @host 同一注册表分派。
  （console.log 垒片亦随 t40 移除：wasm 目标产物不再引用 console。）

## 3. pending-jobs 驱动契约（C3）★ 用户特别要求点

**这是 wasm 目标最重要的宿主契约。**

- 起因：Sublimation 的 `main` 恒为 `async`（编译器决定）；QuickJS 的 promise/async
  语义要求队列里的任务被显式执行，而 **wasm 没有自己的事件循环**——不驱动=程序静默挂起。
- 契约：`evalCode` 之后宿主必须执行

  ```
  while (runtime.hasPendingJob())
      runtime.executePendingJobs(N)   // 可选：唤醒数与总数设上限
  ```

  直到 `hasPendingJob()` 为假。本宿主上限：唤醒 4096 次 / 每轮 2048 任务 / 总 2,000,000
  任务；超限按「不收敛（疑似死循环）」报 C5 错误，不卡死。
- 注意点：
  - 该 API 在 `runtime` 上而非 `context`（`vm.executePendingJobs` 不存在，Phase 0 踩过）；
  - `executePendingJobs` 返回 **number**（执行数）或错误对象（异步任务抛出时），
    两者都要处理；
  - 该循环与 `sleep/delay` 类异步等待不构成事件循环：见 §6。
- **编译器侧义务**（交给 t35）：产物中 main 的 async 粘合代码不得依赖 Node 专属异步原语
  （`setTimeout` 等）；Target 层若引入平台分派，wasm 分支的事件/等待语义须能由宿主
  通过本契约驱动。

## 4. handle 契约（C4）

- 宿主创建的每个 handle（`newObject/newArray/newFunction`、`evalCode` 的   `value/error`、`getProp/callFunction` 结果、桥内构造的临时 handle）**必须 dispose**。
- 实现方式：句柄注册表（本宿主 `HandleRegistry`），结束时逆序统一回收；
  `vm.undefined/null/true/false` 是上下文单例，**不得**注册回收（Phase 0 的
  `list_empty(&rt->gc_obj_list)` 断言就是漏 dispose 引起的）。

## 5. 错误契约（C5）

宿主返回结构化结果 `{ ok, kind, error, lines, jobs }`，kind 分四类：

| kind | 含义 | 典型来源 |
| --- | --- | --- |
| `load` | 模块/产物装载失败 | wasm 模块损坏、app.js 不可读 |
| `eval` | 求值期失败 | 应用代码抛错、桥缺失（ReferenceError） |
| `pending` | 异步任务期失败 / pending-jobs 不收敛 | 异步 main 内抛出、死循环 |
| `host` | 宿主自身失败 | 宿主实现 bug |

- 平台不可用能力必须以**明确错误**暴露，不得静默吞（`wasmFetch` 前瞻声明抛
  「暂不可用 + 落地路径」）。
- **已知缺口（-A 路线）**：今天产物的 `main()` 调用结果被 IIFE 内部丢弃，宿主拿不到
  promise 句柄——若 main 的 rejection 没有留下 pending job，拒绝会**静默**（Phase 1
  实测：桥内抛错当时表现为输出截断 + exit 0）。`--target=wasm`（S-1 导出）落地后，
  宿主持有 `__subl.main()` 的调用结果，才能完整观测拒绝（§7 路线）。

## 6. 异步桥的边界与前瞻声明

`@async` 宿主桥（如 `app/net.subl` 的 `wasmFetch`）在同步宿主下**无法真正等待**。
两条落地路径（留给 Phase 1.5+）：

1. **asyncify 变体**：换 `@jitl/*-asyncify-release-*` 宿主，桥内可以 yield，
   同步语义保真；代价是 wasm 体积与性能。
2. **deferred-promise 协议**：桥返回 pending promise（`vm.newPromise()` 的 deferred），
   宿主在装载后异步 resolve（如 Node 侧真 fetch），再由 C3 循环恢复 awaiting 协程。
   无需换变体，但需要协议规范（何时 resolve、错误如何入 Err 通道）。

本阶段：`wasmFetch` 仅**前瞻声明**（签名先立、运行期明确不可用），把选择权留给
宿主升级窗口，不锁死 API 形状。

## 7. 与编译器 `--target` 的路线关系（对接 t35）

| 路线 | 产物形状 | 宿主行为 | 状态 |
| --- | --- | --- | --- |
| -A 处理器（SfA 式，旧链路） | 自执行 IIFE，main() 立即触发 | 裸名桥已被 ABI 收口移除：旧 -A 产物不再被当前宿主支持 | 历史（不再走） |
| `--target=wasm`（S-1 导出） | `globalThis.__subl = { main, ... }`，不自执行 | 宿主调 `__subl.main()` 再 C3 驱动 | 宿主已适配（§1 步 5），等编译器 |

**宿主已双路线兼容**（S-1 探针实测：合成 `__subl` 产物被宿主正确调用 main 并跑完桥）。
等 t35 落地 `--target=wasm` 后，SfW 主路线切换到 `--target`，-A 路线保留为兼容兜底
（处理器不删、demo 不改默认链路）。
