# SfW 路线选型：WASM 目标怎么落地

本文是 SfW（Sublimation for WASM）的路线决策文档：两条候选路线的论证、选型建议、
分阶段方案，以及**需要的编译器改动清单**（交给队长排期，由编译器核心成员执行；
SfW 侧不改编译器）。

---

## 0. 结论（TL;DR）

**推荐：先 B 后 A（分阶段）。**

- **Phase 0（现在可做，零编译器改动）**：走 SfA/SfG 已验证的**路线 B**——编译器照旧产 JS，
  用 `@postcompile` 处理器把 JS 产物打包进 **QuickJS-in-WASM 宿主**（quickjs-emscripten），
  产出可在浏览器/Node 里加载的 .wasm 应用。先证明「Sublimation 跑在 WASM 上」，
  并把「哪些平台 shim 必要」实验出来。
- **Phase 1（排队给编译器核心）**：落地《安卓标准库设计》§4.2 设计的**路线 A**（Target 层）——
  `Target` 枚举 + `--target=node|browser|wasm` + 平台分支分派 + S-1 导出产物 +
  抑制 main() 自执行 + `E-PLATFORM-UNAVAILABLE`，让 wasm 成为一等编译目标。

理由：生态雏形期**可演示性优先于完美抽象**；B 路线的宿主经验（shim 清单、导出契约）
会直接喂给 A 路线的 `Target.Wasm` 设计，降低 Phase 1 的返工概率；A 的设计文档
（boring doc）已就绪，Phase 1 排期可控；B 是 A 的子集而不是竞争方案——Phase 1 落地后，
Phase 0 的宿主从「产品」降级为 A 的一个后端。

## 1. 背景：现状与硬约束

**编译器现状**（已核实源码）：

- 只有 JS 后端，产物是单文件自执行 IIFE（`"use strict"; (() => { ...; main(); })();`），
  `fun main()` 由 `JsCodeGen.kt:407-413` 自动调用。
- **平台假设硬编码**在 codegen 的平台内建分支里（`JsCodeGen.kt:1126-1151`）：
  `println`→`console.log`；`readLine`→`Buffer+require('fs')`；
  `readFile/writeFile/appendFile/readDir`→`require('fs')`；`fileExists`→`require('fs').existsSync`；
  `getArgs`→`process.argv`；`timeNow`→`Date.now()`、`rand`→`Math.random()`（目标无关）。
- 无 `--target` 概念；模块按目录整树编译（MultiModule），单文件产物。

**生态现状**：

- SfA（安卓）面对同样的「平台问题」，选择了**不改编译器**：`-A` 编译参数 +
  `@postcompile` 打包钩子 + 宿主桥（`__dshAndroid`），已端到端跑通。
- SfG（游戏，本轮任务）用同一模式第二次复现（`@game @host` 无体桥接 + 宿主实现 +
  `@postcompile build` 打包，端到端跑通，23 项冒烟断言全过）。
- 主仓设计文档《安卓标准库设计》§4.2 早已设计了 Target 层（`--target=node|browser|android`），
  **但编译器从未实现**——安卓生态实际是靠 B 路线绕开的。

**目标定义**：SfW = Sublimation → WASM，两个子目标——(a) 交付物是一个 .wasm 模块（不再依赖
宿主装 Node）；(b) 平台能力对齐 wasm 宿主的契约（无 fs/process/console 的 Node 假设）。

## 2. 路线 A：Target 层（设计已就绪，未实现）

**出处**：boring doc《安卓标准库设计》§4.1（产物结构 S-1/S-2/S-3 论证）、§4.2（`--target`）、
§5（平台内建重定向）、§13 第一阶段（分阶段实现路线，第 1057-1065 行）。

**设计内容**：

1. 代码生成器持有 `Target` 枚举，CLI 增加 `--target=node|browser|android|wasm`（默认 `node`，
   向后兼容）。
2. `call()` 里的平台相关分支按 target 分派（§5）。
3. 非 node 目标产物改为 **S-1 返回导出对象的 IIFE**：
   `globalThis.__subl = (() => { ...; return { main, dispatch, version }; })();`——保持封装性，
   提供宿主可调用的明确导出面（单一 `dispatch` 入口是关键设计：宿主侧只需知道一个函数名）。
4. 非 node 目标**抑制 main() 自执行**（由宿主在适当时机调用 `main`）。
5. 新增诊断码 `E-PLATFORM-UNAVAILABLE`：目标不可用的模块/函数在**编译期**报错
   （如 wasm 目标下的 `core/io` 同步 IO）。

**优点**：

- WASM/browser 成为一等目标；平台纪律进编译器（编译期拒绝而非运行期崩溃）。
- 顺带 SfG 受益：KAPLAY 页面正好是 `browser` 目标（S-1 导出让宿主控制启动时机，
  而不是 bare-IIFE 立即自执行）。
- §4.2 指出这层抽象同时解决工程审查 P2-6「桌面假设硬编码」，是有独立价值的重构。

**代价/风险**：

- 改编译器核心（JsCodeGen + Main.kt + Checker/ModuleTree + 测试基线），需要编译器核心成员排期，
  走代码评审；回归面大（现有 JS 产物是 SfA/SfG/IDE/语言服务的共同底座）。
- 设计文档针对安卓写就，`wasm` 目标是新外推：io/process 契约、导出命名、宿主注入方式
  都需要补设计。
- SfA 已经用 B 绕开了 A 的安卓场景，A 的紧迫性长期被推后——这是「设计存在但未实现」的
  现实原因；SfW 想先有东西，不能等。

## 3. 路线 B：处理器 + 打包壳（SfA 已验证）

**内容**：

- 编译器**不改**，照旧产 node 风 JS。
- SfW 提供 wasm 壳工程：把 **QuickJS 编译为 WASM**（quickjs-emscripten，npm 可取，
  v0.32.0，MIT）作为 JS 宿主，宿主侧实现 console/IO/参数等平台 shim。
- 与 SfA/SfG 同构：编译器参数 `-A wasmApp=...`，`@postcompile build` 把 JS 产物与宿主
  打包成可分发的 wasm 应用（一个 .wasm 载荷 + 极小的 JS/HTML 加载器）。

**优点**：

- **零编译器改动**，与生态现有机制（-A / @postcompile / 白名单处理器）完全一致，
  SfG 的布局可以直接复用。
- 立刻可演示：Sublimation 程序编译 → 打包 → 浏览器里跑 wasm。
- 独立演进：壳工程换宿主（quickjs→其他 JS-wasm 引擎）不需要协调整个编译器团队。

**代价/风险**：

- 不是「真编译到 WASM」：是 JS-in-wasm（QuickJS 解释执行），性能是 QuickJS 的水准、
  体积含引擎（`quickjs-emscripten` npm 包解包约 2.4MB，单 wasm 载荷视裁剪而定）。
- Node 假设只能由宿主 shim 覆盖到「壳愿意实现的子集」：console 容易，fs/process 是
  语义重映射（或直接禁用）。平台靠**运行期失败**而非编译期拒绝（对比 `E-PLATFORM-UNAVAILABLE`）。
- 宿主选型受网络/生态影响：本环境 GitHub 不可达，npm 可达——quickjs-emscripten 可取，
  javy（Bytecode Alliance，把 JS 预编译为 wasm 字节码，体积更小）在 npm 上不可取、
  且其对宿主 API 的静态限制较多（适合纯计算，不适合需要动态宿主绑定的场景）。

## 4. 对比与选型

| 维度 | A：Target 层 | B：处理器+打包壳 |
| --- | --- | --- |
| 编译器改动 | 需要（核心） | 无 |
| 首次可演示时间 | 排期依赖编译器核心 | 立刻（Phase 0） |
| 平台纪律 | 编译期（E-PLATFORM-UNAVAILABLE） | 运行期（宿主 shim 或失败） |
| 产物形态 | 真目标（codegen 分派；wasm 仍需宿主配合） | JS 嵌入 wasm 宿主 |
| 性能/体积 | 取决于 wasm 后端实现 | QuickJS 解释执行 + 引擎体积 |
| 生态一致性 | 为 SfA/SfG/GKH 所共享的公共底座 | 与 SfA/SfG 的现有模式同构 |
| 风险 | 回归面大、设计需外推到 wasm | 宿主能力天花板低、非「真编译」 |

**选型：分阶段（先 B 后 A）**，见 §0。关键判断：

- 雏形期，`Sublimation 在 wasm 上能跑` 的可演示价值高于架构完美；
- B 的宿主实验`（shim 清单、导出契约、启动时机）`会直接补全 A 的 `Target.Wasm` 设计；
- A 的设计文档已在主仓（无需从零设计），Phase 1 的改动清单可提前排期（§6）。

## 5. Phase 0 落地方案（B 路线，SfW 侧可执行）

**仓库布局（仿 SfG）**：

```
sublimation for wasm/
  app/                       演示程序 + 目标标准库声明（@wasm @host 桥接）
  wasm-app/                  壳工程：quickjs-emscripten 宿主 + shim
    js/wasm-runtime.js       宿主侧桥接实现（console/参数等 shim）
    build/package-wasm.ps1   打包脚本（处理器调用）
  annotation processer/
    wasm.subs                @wasm 白名单 + @host/@impure/无体校验 + @postcompile build
  test/
    smoke-test.js            Node 加载 wasm 载荷、跑演示程序的冒烟测试
  wasm doc/                  本文 + 后续宿主契约文档
  scripts/sync-deps.ps1      同步主仓 core/
```

**宿主选型**：quickjs-emscripten v0.32.0（MIT；npm registry 可取；ES2023；
宿主绑定 API 成熟）。javy 体积更小但 npm 不可取且动态绑定受限，留作 Phase 1 后的可选后端。

**平台 shim 范围（Phase 0 要实验的点）**：

| Node 内建 | wasm 宿主 shim | 备注 |
| --- | --- | --- |
| `console.log` | 转发宿主输出 | 最基础，必须 |
| `require('fs')` 四件套 + fileExists | 暂不提供，或映射为沙盒文件系统 | 语义重映射，留给宿主决策 |
| `process.argv`（getArgs） | 由宿主注入参数数组 | 简单 |
| `Date.now/Math.random` | 引擎自带，无需 shim | |
| `setTimeout`（sleep/delay） | 宿主提供或 busy-loop | 异步语义在 wasm 里的映射需验证 |

**验收标准（Phase 0）**：

1. 一个 Sublimation 小程序（含控制台输出与少量计算）编译后被打包成 wasm 载荷；
2. 浏览器与 Node 两种加载路径都能运行并输出正确结果；
3. Node 冒烟测试覆盖：宿主初始化 → main 调用 → 输出断言 → 错误传播（未提供能力的明确报错）。

**Phase 0 的产出反过来是 Phase 1 的输入**：shim 表 + 导出契约 + 启动时机全部写进
本文档的后续修订（`wasm doc/宿主契约.md`），作为 `Target.Wasm` 的设计依据。

## 6. Phase 1 编译器改动清单（交给队长派发；SfW 侧不执行）

| # | 改动 | 位置（已核实） | 说明 | 阻塞性 |
| --- | --- | --- | --- | --- |
| 1 | `Target` 枚举 + `--target` CLI 参数 | `Main.kt` 参数解析 + Pipeline | 默认 `node` 兼容现状；先加 `wasm`/`browser`；android 目标与 SfA 现状（B 路线）先不强制迁移 | 高（其余改动的前置） |
| 2 | `call()` 平台分支按 target 分派 | `JsCodeGen.kt:1126-1151` | 至少 6 处：`println`→console（1126-1129）、`readLine`→Buffer+fs（1134）、`readFile/…/readDir`→fs（1136-1146）、`fileExists`（1143-1144）、`getArgs`→process.argv（1149-1151）；`timeNow`/`rand`（1147-1148）目标无关可保留 | 高 |
| 3 | 产物结构 S-1（导出对象的 IIFE）+ 抑制 main 自执行 | `JsCodeGen.kt:407-413`（main 自动调用处）+ 文件级 IIFE 包装 | 新目标导出 `{ main, dispatch, version }` 并不自动调 main；node 目标保持现状（§4.1 的 S-1/S-2/S-3 对比，推荐 S-1） | 高 |
| 4 | `E-PLATFORM-UNAVAILABLE` 诊断 | Checker/ModuleTree + DiagCoverage | 目标不可用能力编译期报错（wasm 下 `core/io` 同步 IO、`process.argv` 等）；需模块级 target-可用性表（§9.1 `core/android` 先例：仅 `--target=android` 下可用） | 中（可与 2 同期） |
| 5 | 宿主桥接命名空间 | JsCodeGen + 处理器约定 | wasm 宿主 import 的统一入口（建议单一 `dispatch` 函数，对齐 §4.1 的单入口设计，别走逐个挂全局） | 中 |
| 6 | 各 target 产物快照/基线测试 | codegen 测试 | 防回归（现有 golden 测试的扩展） | 低 |

**与《安卓标准库设计》文档的对齐说明**：§13 第一阶段的 1/2/3 条就是本清单的 1/2/3
（原文以 android 为例；本文把 wasm 套进同一框架）。该文档第 1057 行原文：
「代码生成器引入 `Target` 枚举，CLI 增加 `--target=node|browser|android`（默认 `node`，
保持向后兼容）」——SfW 建议把 `wasm` 加进同一枚举。

## 7. 与 SfA/SfG 的关系

- 三条目标线（Android/Game/WASM）共用同一桥接思想：`@host` 无体声明 + 宿主实现 +
  处理器纪律（白名单/态度校验）+ `@postcompile` 打包。
- Phase 1 的 Target 层是公共底座：落地后 SfA 可逐步从 B 路线迁入 `--target=android`，
  SfG 的 KAPLAY 页面正好是 `browser` 目标（S-1 导出让页面控制启动时机），
  SfW 的 wasm 宿主成为 `wasm` 目标的一个后端——三条线收敛到同一编译器抽象。
- 本轮 SfW 的交付边界：骨架 + 本文档（路线已定、改动清单已列）；Phase 0 的壳工程实现
  等队长确认路线后开工（交付物预估：一个可跑的 wasm 应用 + 冒烟测试 + 宿主契约文档）。

## 8. Phase 1 现状（更新）

Phase 0（-A 路线验证）与 Phase 1（本仓投产化）已完成；正式目标层等 t35：

- **已完成（仓内）**：宿主规范 v1（`wasm doc/宿主规范.md`：C1-C5 契约，含用户要求的
  pending-jobs 驱动契约）、平台边界表（`wasm doc/平台边界.md`）、wasm 目标标准库层
  （`app/wasm.subl` 信息桥 + `app/storage.subl` 存储桥 + `app/net.subl` 前瞻声明）、
  宿主投产化（wasm-runtime.js + 浏览器 ES 宿主）、可部署物打包链
  （`@postcompile build` → 含 wasm 运行时 + app.js + html/node 装载器的自包含产物）。
- **两条路线的关系（宿主已双路线兼容）**：
  `-A 路线`（现在）= 自执行 IIFE；`--target=wasm`（t35 后）= S-1 导出，宿主已实现
  `__subl.main()` 兼容路径并用合成产物探针验证（宿主规范 §1 步 5、§7）。
  t35 落地后 SfW 主路线切 --target，-A 保留为兼容兜底。
- **路线选型的验收**：原计划的 6 项编译器改动清单（§6）保持不变，新增两项精确化：
  - 改动 3（S-1）对 wasm 目标为**必需**而非可选——`-A` 路线下 main 的 rejection
    宿主无法观测（宿主规范 §5 的静默拒绝缺口），S-1 才让宿主持有 main 的调用结果；
  - 改动 5（宿主桥命名空间，建议单一 dispatch 入口）与 SfW 现状的冲突点：
    SfW 的 C2 契约是逐个挂全局（裸名直调，最小编译器假设）。若编译器统一走 dispatch，
    需要同步改宿主与三条线的处理器白名单——建议留作三线协调项，不要单方面推进。
- **S-1 落地后切换计划**：`--target=wasm` 可用即把 demo 与打包链主链路切到 --target
  （编译命令加 `--target wasm`，`@postcompile` 不变），冒烟测试增 "S-1 路线" 对照组
  （现有 18 项保留，增至双产物），`-A` 链路继续跑回归。
