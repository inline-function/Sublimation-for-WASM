# SfW 平台边界表（wasm 目标）

Sublimation 标准库是按 Node/桌面形态写的；wasm 宿主（QuickJS-in-WASM）没有 Node 运行时，
于是标准库的若干能力在 wasm 下不可用。本文是**正本边界表**：哪些可用、哪些不可用、
编译期拒绝的归属、以及给 t35 的接口清单。

> 同一信息在编译器侧的归属：`E-PLATFORM-UNAVAILABLE`（Target 层，t35 实现）;
> 宿主侧的兜底：明确错误而非静默（宿主规范 C5）。

---

## 1. 可用能力（经实测）

| 能力 | 落地方式 | 备注 |
| --- | --- | --- |
| 纯计算（Nat/Int/Rat/Str/List/Map/Set/Optional/Result/when …） | QuickJS 引擎 | core 全量纯函数层 ✓ |
| 控制台输出（`print`） | 编译器特判 `console.log` + 宿主注入 console | 规范 C2 |
| 时间（`timeNow`） | QuickJS 自带 `Date.now` | 无需 shim |
| 随机（`rand`） | QuickJS 自带 `Math.random` | 无需 shim |
| JSON（core.json） | 纯 JS | ✓ |
| 字符串/正则/数值库 | 纯 JS | ✓ |
| 宿主桥：`wasmName`/`wasmTimeMs`/`wasmEnv` + `wasmStorage*(6)` + 前瞻 `wasmFetch` | `globalThis.__subl.call(op, args)` 单入口分派宿主侧 op 注册表 | 规范 C2（v1.1） |
| 宿主存储：`wasmStorageLoad/Store/Has/Remove/Keys/Clear` | 宿主 KV（Node=Map，浏览器=localStorage） | Phase 1 新增 |

## 1b. 宿主桥 op 表（__subl.call 的 op 名；与处理器白名单一一对应）

| 类别 | op 名 | 说明 |
| --- | --- | --- |
| 输出 | `println`（`print` 映射于此）、`print` | 参数已 __dshtoStr；浏览器宿主 print 直连 console.log |
| 命令行 | `getArgs` | 宿主注入参数（List[Str]） |
| 等待 | `sleep` | wasm 同步宿主不可用（宿主规范 §6），抛明确错误 |
| 信息 | `wasmName` / `wasmTimeMs` / `wasmEnv` | 宿主名/时钟/环境表 |
| 存储 | `wasmStorageLoad/Store/Has/Remove/Keys/Clear` | Optional[List[Str]]/Str/Bool/List[Str] |
| 网络（前瞻） | `wasmFetch` | 暂不可用，错误指明落地路径 |

## 2. 不可用能力（须编译期拒绝：E-PLATFORM-UNAVAILABLE）

| 能力 | 编译产物里的 Node 假设 | wasm 宿主现状 | 拒绝归属 |
| --- | --- | --- | --- |
| `readFile` | `require("fs").readFileSync` | 无 require、无 fs | 编译期（t35） |
| `writeFile` | `require("fs").writeFileSync` | 同上 | 编译期（t35） |
| `appendFile` | `require("fs").appendFileSync` | 同上 | 编译期（t35） |
| `readDir` | `require("fs").readdirSync` | 同上 | 编译期（t35） |
| `fileExists` | `require("fs").existsSync` | 同上 | 编译期（t35） |
| `readLine` | `Buffer + fs.readSync(0,...)` | 无 stdin | 编译期（t35） |
| `getArgs` | `process.argv.slice(2)` | 无 `process` | 编译期（t35） |
| `sleep`/`delay` | `new Promise(r=>setTimeout(r,...))` | 无事件循环 setTimeout | 编译期（t35） |

**为什么拒绝必须落在编译期（处理器做不到）**：`annotation processer/wasm.subs` 的
处理器 API 只有按名字的查询（funNames/funHasAnnotation/…），**看不到调用点 AST**；
「应用调用了 readFile」这一事实在处理器层面不可观测，只能在编译器 Target 层分派。
宿主侧的现实是：调用了这些桥的程序在 wasm 里以 ReferenceError/能力缺失告终
（错误清楚、不静默——规范 C5），但这不是好体验，所以编译期拒绝是正式路径。

## 3. 前瞻声明（已立签名，实现待宿主升级）

| 声明 | 形状 | 落地阻塞点 |
| --- | --- | --- |
| `wasmFetch(url): Result[Str, Str]`（`@async`） | 宿主侧 fetch → Result | 同步宿主无法等待 IO（宿主规范 §6：asyncify 变体或 deferred-promise 协议） |

## 4. 给编译器线（t35 已落定部分 + t37 待落定部分）的接口清单

1. **`--target` 取值**：需要 `wasm` 之分（与 node/browser 并列）；SfW 用它走 S-1 路线。
2. **S-1 导出形状**（正本：宿主规范 §7）：`globalThis.__subl = { main, ... }`，
   `main` 为 async、由宿主调用（宿主已实现并探针验证）。
3. **main 自执行抑制**：`--target=wasm` 时产物末尾不得自调 main（IIFE 保留结构、去掉调用）。
4. **平台分派点**：`JsCodeGen.kt` 的 IO/进程/等待相关分支（readFile/writeFile/appendFile/
   readDir/fileExists/readLine/getArgs/sleep 八项，对应 §2 表），wasm 分支定位
   `E-PLATFORM-UNAVAILABLE` 报错而非生成 Node 代码。
5. **async 粘合的平台中立**：wasm 产物的异步胶水不得引入 setTimeout/process（宿主规范 C3）。
6. **op 白名单（t38 更新）**：处理器白名单按 **op 名**维护（op 名 = `@wasm @host` 声明的函数名；`print` 的 op 为 `println`，由编译器内建桥分派）。宿主 op 注册表与本表一一对应。
7. **宿主桥 ABI 已统一定案（t38）**：队长裁决唯一入口 `globalThis.__subl.call(op, args)`——此前「裸名直挂」（SfW v1 规范 C2）与「单独 dispatch 命名（`__subl.d`）」作废，统一拦截点供插件框架/处理器 op 白名单/能力门控使用。宿主侧已按新 ABI 实现（OPS 注册表）；编译器侧由 t37 落定（op 名生成、`--target` 下 `@host` 调用改走单入口）。下游用注入 `__subl.call` 的桩实测（test/dispatch-abi-test.js，13 项全过）；过渡期宿主保留裸名别名与 console.log 垫片（同一注册表派生），t37 落定后移除。
8. **-A 路线保留**：`wasm.subs` 处理器不删除，物理隔离新旧两条链路（切换期可灰度）。

> 复用前提：SfA 与 SfG 共用同一编译器，期望 S-1/平台分派设计对三者通用
>（SfA 早已表达过同方向的需求）——具体由队长与编译器线协调，本文只锁 SfW 侧接口。
